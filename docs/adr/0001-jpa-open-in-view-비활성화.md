# 0001. JPA open-in-view 비활성화

- 날짜: 2026-09-22
- 상태: 채택
- Phase: 0

## 맥락

Spring Boot는 `spring.jpa.open-in-view`가 기본 `true`다. 이 값이 켜져 있으면 영속성 컨텍스트(EntityManager)가 트랜잭션 종료 후에도 HTTP 요청이 끝날 때까지 살아 있다. 덕분에 컨트롤러와 JSON 직렬화 단계에서도 lazy 로딩이 동작한다.

Open Session In View라는 이름 그대로 JSP·Thymeleaf 서버사이드 렌더링 시대의 해법이다. 뷰 템플릿이 트랜잭션 종료 뒤에 실행되므로, 세션을 열어두지 않으면 화면을 그리다가 `LazyInitializationException`이 터졌다. 이 프로젝트는 REST API만 제공하고 서버사이드 렌더링을 하지 않는다.

제약:

- **정합성** — 트랜잭션 커밋 후 나가는 lazy 쿼리는 어떤 트랜잭션에도 속하지 않는다. 각각 별개의 auto-commit 읽기가 된다. 결제·정산 도메인에서 "이 읽기가 어느 트랜잭션에 속하는가"는 판단의 기본 전제다.
- **성능 측정** — Phase 1에서 2,000 VU 부하 테스트로 커넥션 풀 병목을 관측할 계획이다. OSIV가 켜져 있으면 커넥션 점유 구간이 트랜잭션 경계와 달라져 측정값의 해석이 어려워진다.
- **학습 목표** — N+1 탐지와 트랜잭션 경계 설계가 이 프로젝트의 목표다. OSIV는 직렬화 단계에서 쿼리를 조용히 발생시켜 N+1을 숨긴다.

## 선택지

| 안 | 장점 | 단점 | 금융 도메인 위험 |
|---|---|---|---|
| A. `true` (기본값 유지) | 컨트롤러·직렬화에서 lazy 접근이 자유롭다. 조회 코드를 미리 설계하지 않아도 동작한다 | 커넥션 점유 구간이 길어진다. 트랜잭션 밖 쿼리가 발생한다 | 트랜잭션 경계가 흐려져 정합성 판단 근거가 사라진다. N+1이 예외 없이 숨는다. 외부 PG API 호출이 뒤에 붙으면 그 시간만큼 커넥션을 붙잡아 풀 고갈 위험 |
| B. `false` | 영속성 컨텍스트가 `@Transactional` 경계와 일치한다. 트랜잭션 밖 lazy 접근은 예외로 즉시 드러난다 | 서비스 계층에서 fetch join 또는 DTO 변환으로 필요한 데이터를 미리 확정해야 한다. 조회 설계 비용이 앞당겨진다 | 없음. 오히려 경계 위반이 런타임에 조기 노출된다 |

## 결정

**B (`false`)를 채택한다.**

`application.properties`에 명시한다.

```properties
spring.jpa.open-in-view=false
```

이유는 셋이다.

1. 서버사이드 렌더링을 하지 않으므로 A의 유일한 장점이 이 프로젝트에 해당하지 않는다. 서버에서 "뷰 렌더링"에 해당하는 것은 Jackson의 JSON 직렬화뿐이고, 여기서 lazy 로딩이 일어나는 것은 이득이 아니라 사고다.
2. B의 단점(조회 설계 비용이 앞당겨짐)은 이 프로젝트에서 비용이 아니라 목적이다. 어떤 데이터를 어느 트랜잭션에서 읽을지 명시하는 훈련이 학습 목표에 포함된다.
3. Prisma는 lazy 로딩이 없고 `include`/`select`로 명시 로딩한다. B가 기존에 쓰던 모델과 일치하므로 전환 마찰이 작다.

Spring Boot가 기본값을 `true`로 두는 것은 하위 호환 때문이며, 부팅 시 WARN으로 인지를 요구한다. 신규 프로젝트에서 이 기본값을 따를 근거로 보지 않는다.
